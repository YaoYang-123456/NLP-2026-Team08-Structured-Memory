# 第二阶段：证据补齐诊断与训练历史准备

这是外部 AI 辅助证据审计，不是人工验收。实验结论见[第二阶段主报告](metamem-stage2.md)。本文件只描述生成前固定的证据操作和独立质量标准，不预写改善结论。

## Oracle 诊断固定输入

脚本 `scripts/prepare_stage2_evidence.py` 使用第一阶段的 `output/stage1-evidence/validation-history.json` 原史缓存，只处理晚餐 `06f04340` 和首饰 `9d25d4e0`。这两题已由参考答案和人工分析方向定位，因此属于 **reference-assisted oracle**；它不构成可部署检索算法，不能将效果称为自动检索提升。

补齐条件仍以现有 180 词分块方式构造逐字来源 chunk，保留日期、角色和 fact ID。先放下面的必要事实，再按原 BM25 顺序补入不重复的原检索项。最多20条、正文总长最多12000字符，尾项沿用字符截断规则。必要事实排到前面同时改变了覆盖与组织位置，因此任何改善也不能纯归因于“多了一条事实”；它回答的是补齐并前置证据后的能力诊断，不建立严格能力上界。

|题目|固定必要来源|时间、角色|支持的事实|

|晚餐|`answer_92d5f7cd:0:0`|2023/05/23 00:29，user|请求使用新鲜 basil 和 mint 的食谱|
|晚餐|`answer_92d5f7cd:4:0`|同上，user|近期用 basil/mint 做菜；从自家花园收获 cherry tomatoes|
|首饰|`answer_fcff2dc4_1:0:0`|2023/05/28 09:02，user|上个月15日得到银项链，日期应是4月15日|

|首饰|`answer_fcff2dc4_1:8:0`|2023/05/28 09:02，user|一个月前得到订婚戒指，待改尺寸|

没有把参考数字3或参考食材列表改写成新的“记忆”。原史中同一个戒指还有 `answer_fcff2dc4_3:0:0` 的重复叙述，本次不重复插入，以免把同一事件误充为两个获得物。基线已有项链、耳环，新补戒指；晚餐原检索没有目标食材会话。

首饰原问题使用 pieces，参考将一对耳环计为一个获得物的口径仍需说明，不因 oracle 而消失。香草是否也自种没有如 cherry tomatoes 一样明确的原史断言；不能把“在做菜时使用”扩成“用户亲自种植”。

## 晚餐的预先固定附加指标

`output/stage2-preparation/oracle-quality-policy.json` 在生成前保存，版本 `stage2-oracle-quality-v1`。外部 AI 评审使用完整回答和原史片段，人工字段保持空。它不替代严格拒答 v2 下的原偏好题评分。

- `basil_or_mint_correctly_used`：实际建议的晚餐是否具体使用 basil 或 mint，且不与来源矛盾。
- `cherry_tomatoes_correctly_used`：实际建议的晚餐是否具体使用 cherry tomatoes，且不与来源矛盾。
- `necessary_evidence_correctly_used`：上述两组均正确使用才为 yes；任一缺失或误用为 no；其余无法消解的歧义保留 uncertain。仅在无关段落提到食材不算使用。
- `unsupported_personal_attribution`：是否无依据断言用户喜好、经历、食材持有或来源。普通菜谱建议、明确条件式假设不自动算个人事实；断言“你自种的 basil/mint”则需要原史支持。保存对应原文和理由。

前几个字段测量输出内容与证据的一致性，**不是模型因果利用记忆的证明**。即使基线没检索到该会话，也可能凭通用菜谱先验碰巧提出相同食材。

## 二十条训练历史与泄漏边界

训练原史缓存由同一官方原始 JSON 数组增量解析，只保留 `data/pilot/train.inputs.json` 中20个 ID，按既有顺序保存。其他记录被解析后立即丢弃，不打印、不查看问题或答案；没有打开测试输入或标签。此过程不应描述为完全未触及原始文件中的其他字节。

- `train-history.json` 是训练专用原史审计缓存，含训练参考标注；只用于必要的来源定位，不能直接给运行时检索器。
- `train.history-inputs.json` 通过白名单保留 question/id/type/date 和 history 的 session ID、日期、role、content。删除 answer、answer_session_ids、has_answer 等字段；可部署检索候选只使用这一文件。
- `oracle.inputs.json` 格式与现有 validation.inputs 一致，仅两条补齐输入，不含参考答案。
- `oracle-diff.json` 保存每题原/新 fact ID、字符数、哈希、加入和移出项，以及必要原文、角色、时间、turn/chunk。
- `verification.json` 保存原始来源哈希、生成文件哈希、边界说明与基线复现结果。

## 实际检查和复现

在仓库根目录执行：

```powershell
.venv/Scripts/python.exe scripts/prepare_stage2_evidence.py
```

脚本拒绝覆盖已有准备目录。复现应在独立干净副本中恢复相同原始数据与第一阶段缓存后执行；现有研究产物不要删除后重建。

检查包括：两条 oracle 原史重跑原 retrieve 与冻结 baseline 完全一致；20条训练原史重跑与训练输入完全一致；去标注后再重跑20条亦完全一致。检查证明来源和实现对齐，不是召回率或语义正确率。算法候选的训练审计、完整开发集事实差异及回答结果由主实验材料另行记录。

以上本地缓存和原始产物保留在 Git 忽略的 output 中，代码与说明进入仓库；本次证据准备子任务没有调用本地模型。

### 时间边界没有修复

观鸟问题仍有6条检索事实的会话时间晚于问题时间；两个条件完全相同。关键工作坊会话20:08晚于提问19:31，共37分钟。其余9题按记录日期检查均没有候选事实晚于问题时间。当前候选不是时间过滤方案，不能将其成绩解释为解决了截至时间正确性。

Oracle 的实际正文为晚餐20条/9306字符、首饰20条/12000字符；原条件分别20条/9996字符、19条/12000字符。两条件上限一致但实际长度不严格相等，且补齐项前置。主对照自动候选的实际长度也见上表，必须保留这些差异而非宣称输入token完全一致。
