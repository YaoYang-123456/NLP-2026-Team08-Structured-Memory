# MetaMem 小规模课设试点方案

日期：2026-10-15。状态：可讨论、可执行的准备方案，尚未开始真实模型实验，尚未确定为全组最终选题。它同时服务杨垚的 MetaMem 阅读；不自动分派其他成员任务。相关依据见 [论文比较](../notes/paper-comparison.md)、[阅读笔记](../notes/05-metamem-YaoYang-123456.md) 和 [代码审阅](metamem-code-review.md)。

## 目标与研究问题

在固定事实记忆、检索结果和回答模型的条件下，比较“无经验规则”“人工固定规则”“训练学到的规则”。检验元记忆是否帮助模型处理时间关系、知识更新、多会话信息整合，以及收益是否值得额外调用成本。第一轮目标是验证闭环和估算成本，不承诺统计显著或达到论文准确率。

建议采用 MetaMem 已支持的 RAG 场景开始：论文 Table 2 已测试 RAG 加元记忆。这样可暂时降低 LightMem 构建的工程负担，但必须标注“RAG 场景小规模验证”，不能称为完整 LightMem 主表复现。若优先要求与主表一致，则改用 LightMem，单独计入事实记忆构建成本。

## 第一轮范围

| 项目 | 试点建议 | 与原论文的区别 |
| --- | --- | --- |
| 数据 | 使用官方 README 指向的 LongMemEval S cleaned；先选 50 条形成固定清单，保存 ID、类型和源文件哈希 | 原文是 500 条五折 |
| 划分 | 20 训练、10 验证、20 测试；固定 seed 42，先检查同用户/历史关联，尽可能保持类型覆盖 | 属于项目自定试点协议，不声称原文划分 |
| 冒烟检查 | 从训练集合取 5 条，检查生成、judge、规则更新和落盘 | 不用于报告正式精度 |
| 模型 | 一种可访问的回答模型＋固定 judge；具体名称、版本、量化与服务地址在启动前记录 | 不假设能在单张 16GB 卡直接按官方默认部署大模型 |
| 学习 | 初始尝试 1 epoch、batch 5、每题 2 次采样 | 原文为 5 epochs、batch 50、每题 5 次 |
| 检索 | 同一个 embedding 模型、top-k 和上下文预算；结果预计算后给三组共享 | 不边换检索器边比较规则收益 |
| 上下文 | 事实区与规则区分别设预算，保留相同事实证据；记录实际 token | 规则带来额外输入，应计入成本 |
| 测试 | 按验证结果选一个规则版本；测试集只做冻结后的比较 | 不靠看测试答案反复改提示词 |

如果按用户或历史分组后无法恰好得到 20/10/20，应先保持分组隔离，记录实际数量，再调整计划；不能为了凑数拆开同一组。真实数据结构和分布尚未核验，这一项不能提前打勾。

## 三个必要实验组

| 组 | 设置 | 用来回答什么 |
| --- | --- | --- |
| B0 | 相同事实 M，E 为空；显式使用空规则文件 | 没有元记忆时的基准表现 |
| B1 | 相同 M，加一份在看测试集前写定的少量通用规则 | 简单提示词是否已经足够 |
| B2 | 相同 M，加仅从训练集学到、由验证集选择的规则 | 数据驱动演化是否比前两者有额外收益 |

三组共享提问、事实排序、回答模板的其余部分、采样参数和 judge；B1、B2 使用相同规则 token 上限。不得为了适配某一组截掉不同的事实。B0 没有规则产生的额外输入差异必须计入 token 成本；若之后要归因“规则语义”而非“更多输入”，再做长度匹配对照，第一轮不增加无关组。

B1 可以从“区分总量与部分”“检查事件和时间背景”“证据不足时不编造”等一般原则出发，但要在查看测试答案前冻结。B2 若没有产生规则，仍如实报告；结合上游部分正确筛选检查原因，不能悄悄手填规则再称为学习结果。

## 调用预算怎样估算

设训练问题数 N、每题采样 k、轮数 e、batch 大小 b。仅生成和 judge 就约为 `2 × N × k × e` 次请求。若每个采样都反思、每题提出一次修改、每批合并一次，规划时可近似按 `e × (3Nk + N + ceil(N/b))` 估算学习调用数，不含构建事实、嵌入、验证、测试、失败重试或额外修复请求。

试点 N=20、k=2、e=1、b=5 时，上式为 144 次；上游会筛掉全对/全错组，所以实际反思数可能更少。若评估 4 个规则版本、每次 10 条验证题，则生成与 judge 约再加 80 次。最终三组各 20 条测试约再加 120 次，总计约 344 次，加上前述未计项。**这只是请求数量估算，不能换算成固定价格或保证额度够用。**原配置单折 350×5×5 已有 8750 次回答生成和同数量 judge，尚未算反思等。

先从 5 条训练样本测出各阶段平均输入输出 token，再按所选服务实际计费或本地耗时推算预算。不要把聊天订阅额度直接当作实验 API 余额。超出计划时先缩小验证频次或样本数，并记录协议变化。

## 结果记录与完成标准

每次运行保存：配置、数据清单、规则版本与哈希、题目 ID、任务类型、检索到的事实 ID、模型回答、judge 输出、错误状态、token、分阶段耗时。原始数据和逐题输出留在 data/、output/，仓库提交运行入口、配置模板、汇总和必要的去标识案例。

汇总至少含每组总样本数、成功生成数、有效评分数、正确数、覆盖率、总体和分类准确率、总调用与 token、实际耗时。服务错误不悄悄混为推理错误；同时报告所有预定题目的完成情况。比较时用相同题目，列出 B0 错而 B2 对、B0 对而 B2 错的配对案例。20 条测试一题就是 5 个百分点，不以小幅波动宣称普遍有效。

满足以下条件才进入扩大实验：三组均完成同一批样本；能确认没有把答案传入回答模型；规则确实加载且冻结；错误率和成本可解释；可以从保存的命令和配置复跑。若只跑通调用而无可解释比较，阶段名称仍是“管线跑通”。

## 后续一个可检验的改动

候选：给元记忆增加“适用条件”，例如只在问题涉及当前状态时优先近期事实，避免把“最近的总是优先”错误用于历史问题。研究假设是条件化经验能减少错误泛化。它是待检验的课设改动，不宣称学术首创。

只有 B0–B2 跑稳后再加入 B3；同等规则预算下比较，另做去掉条件的消融。若改动无提升，报告适用范围和失败原因也有价值。不要同时改模型、检索、规则结构和评判器，否则不能解释变化来源。
