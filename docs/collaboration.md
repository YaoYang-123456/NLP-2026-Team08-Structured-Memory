# 小组协作与文件约定

## issue 分工

- 本仓库公开可见，任务认领、issue、PR、提交说明和公开材料使用 GitHub 用户名，不填写成员真实姓名、学号等个人身份信息。
- 6 人共用 issue 作为任务清单。一项可以独立验收的工作对应一个 issue，例如一篇论文的阅读总结、一个实验或报告的一章；修正错别字等附带小改动可随原任务完成，不必逐项建 issue。
- issue 写清目标、负责人、产出路径和完成条件；有依赖或约定截止时间再补充。一项任务指定一位负责人，其他成员可以协助。
- 开始前认领或分配 assignee；涉及同一个文件时，先在 issue 中约定编辑范围。只在出现阻塞、范围变化或完成时更新进度，不要求频繁汇报。
- 微信群用于快速讨论和大文件传输；影响任务范围、分工或接口的结论简要同步到对应 issue，便于后续查找。

## 分支和 PR

1. 从最新 `main` 新建任务分支，命名为 `<用户名>/<issue编号>-<简短主题>`，例如 `hycx233/12-structmem-notes`。
2. 只提交本任务及必要配套改动。提交说明使用简洁的 `docs:`、`feat:`、`fix:` 或 `chore:` 前缀，说明具体变化；无关修改留在各自分支。
3. 完成后向 `main` 提 PR，正文关联 `Closes #编号`，简要说明改动、实际验证和已知问题。尚未完成可用 Draft PR；不要把未运行的检查写成通过。
4. 作者先检查 diff、文件路径、引用和适用的运行或构建结果，再按下面规则决定是否请求成员审核。合并后关闭 issue；已使用 `Closes` 的由 GitHub 自动关闭。

## 审核不过度打扰

- 任务认领及分工登记属于小改动，自查后直接合并，不挂起等待成员审核；认领 PR 用 `Refs #编号` 关联技术任务，避免登记合并就关闭尚未完成的任务。遵守实际分支保护。
- 每个 PR 都需要作者自查。普通独立任务（个人阅读笔记、文档修正、已约定范围内且不影响他人的小改动）自查通过后，作者可自行合并；不要求另一人批准每个 PR。
- 涉及公共接口、共享数据格式、项目依赖、他人正在修改的部分，或小组最终报告与提交材料时，请一位最相关的成员审核。提交审核前整理好完整结果和验证信息，一次说明需要关注的问题。
- 不要默认请求全组审核，不要为排版、命名等低风险细节反复催审。已审核后的同范围小修正，补充说明即可；出现新的实质影响再请相关成员复核。
- 如果仓库实际分支保护要求批准，遵守该要求；无权限合并或审核阻塞时，在对应 issue / PR 中说明具体原因。不要为绕过保护改配置。
- AI 助手应按当前任务授权推进实现、自查及 Git 操作，不因“最好再请人看一下”而停下；真正需要协作决定时提出具体问题，不以泛化风险为由反复索要确认。

## 文件与格式

- 平时作业和课设由同一小组在本仓库推进，围绕同一专题共享论文、笔记和引用。平时作业先形成系统性综述，课设在其基础上开展实现和实验；阅读报告不以尚未完成的课设实验为提交前提，也不将论文结果写成本组复现结果。
- 新文件和目录优先使用简短英文名称，以小写和连字符分隔；代码中的命名遵循所用语言。老师原始文件和现有论文文件保留原名、原文。
- 阅读笔记建议使用 `notes/01-structmem-<用户名>.md`；公共汇总放在 `reports/`，避免各自创建名称相同的“最终版”。必要版本用 `YYYY-MM-DD` 区分。
- 平时作业统一编辑 `reports/homework/main.tex` 和 `sections/` 下各论文章节，一人一篇，在 issue 中认领具体章节；跨论文比较、PPT 和讲解由全组共同整合。各成员填写真实分工及贡献百分比，汇总为 100%。截止日期、视频时长和编译方法见[平时作业说明](../reports/homework/README.md)。
- 报告使用 LaTeX 编写、PDF 交付，官方 Word 样例用于对照排版；不要求成员维护平行 DOCX 版本。编译缓存和预览 PDF 放 `output/`；定稿后将小于 20 MB 的最终 PDF 及 PPT 放入 `reports/homework/`，视频按大文件约定交接。
- Slides 使用 `reports/homework/slides/` 的共享 Beamer 版式并导出 PDF；每人编辑自己的模块，开场和总结统一整合。时间安排、个人预览与讲稿备注见 [slides 说明](../reports/homework/slides/README.md)。
- 文本文档使用 UTF-8、LF 换行，文件末尾保留换行；默认 4 空格缩进，YAML / JSON 使用 2 空格。Markdown 以清晰标题和段落为主，使用相对路径链接仓库资料。
- 笔记至少说明论文的问题、方法、关键实验、局限和对课设的启发；引用标注论文及页码 / 图表编号。区分论文结论、实际复现结果和自己的推测，不编造实验数据。
- 提交必要的可编辑报告源文件；小于大文件阈值的最终导出文件可放在 `reports/`。缓存、临时编译文件、运行输出放在 `tmp/` 或 `output/`。
- 原始数据和密钥保留在本地；不提交 `.env`、访问令牌、带个人信息的数据。需要共享配置时提供不含秘密的 `.env.example`。

## 大文件传输

- 单文件达到 **20 MB（20,000,000 字节）**，包括视频、大型 PPT、数据集、模型权重和压缩包，明确提醒用户：**“请将该文件发送到小组微信群。”**
- 不将这类文件加入 Git 历史或 PR 附件，也不为此自行引入 Git LFS、网盘或额外传输服务。
- 在对应 issue 或相关文档记录文件名、大小、用途、发送人及群内发送日期；能计算时附 SHA-256。收到文件后按说明放在本地 `data/`、`output/` 等适用目录。
- 若大文件必须作为最终提交材料，仍通过微信群交接，在仓库记录对应版本和提交说明。
